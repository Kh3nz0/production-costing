### 1.1 Dashboard aggregates

Twelve queries, each independently streamable so a slow one cannot block the rest: inventory value · production cost this month · revenue this month · contribution profit this month · average contribution margin · waste rate by value · failure rate · overhead recovered vs pool · rolling 12-month revenue vs ₱3,000,000 · low stock · products below target margin · cost increases vs 30 days ago · recent purchases, runs, sales.

**No dashboard card may exist that a report cannot reproduce.** If a figure appears only on the dashboard, either the report is missing or the card is wrong.

## 2. RPC surface

Six functions. Each is `security definer`, org-scoped from `auth.uid()`, and wholly transactional.

| Function                                       | Guarantees                                                                                                                                                                                                                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `receive_purchase(purchase_id, lines[])`       | Locks each item row, allocates added costs by the chosen base, writes `purchase_received` movements, recomputes the weighted average, stores `receipt_unit_cost` and the resulting running average on each movement. Refuses a quantity base when line units span dimensions |
| `complete_production_run(run_id, actuals)`     | Writes consumption, output, failure and waste movements; splits normal from abnormal failure; recomputes the finished-goods average from the capitalised cost only; writes the immutable `rate_snapshot`; sets status `completed`. All or nothing                            |
| `reverse_production_run(run_id, reason)`       | Writes opposite movements, sets status `cancelled`. Never deletes                                                                                                                                                                                                            |
| `record_sale(sale, lines[])`                   | Draws COGS from the finished-goods average at that moment, writes `sale` movements, stores fee **amounts**, computes and stores revenue through contribution profit. Refuses uncosted stock unless `cost_source='estimate'` is passed explicitly                             |
| `adjust_stock(item_id, new_qty, reason, type)` | Writes one `adjustment` movement. Refuses a negative result on a costed item. Never changes unit cost                                                                                                                                                                        |
| `rebuild_item_balances(org_id)`                | Recomputes `qty_on_hand` and `avg_unit_cost` from the ledger. Asserted equal in tests                                                                                                                                                                                        |

Everything else is ordinary PostgREST with RLS.

Fourteen stages. Each is a thing that works and can be shown. No stage starts before the previous one's "done when" is observably true.

**Sequencing notes.** S3 precedes S4 because the ledger's shape is decided by what a receipt must record. S6 cannot precede S5 because a breakdown with no rates cannot be judged. S10 is late because a dashboard built before the reports is a set of numbers with no source. S13 is late deliberately — onboarding is the least-used screen in the product and the easiest to get wrong before the things it configures exist.

**There is no "polish" stage and no "make it responsive" stage.** Responsive behaviour and all ten screen states are inside each stage's done-when.

## 5. Technical constraints

Five are real and one of them has already changed the design. Each is stated with its consequence.

**5.1 Decimal precision must survive the wire.** Postgres `numeric` arriving as a JavaScript `number` loses exactness, and `19.32 × 1.203083` will drift at the fourth decimal — visible on the cost breakdown, which shows four. Request numeric and bigint monetary columns with **`::text` projections** and preserve the strings through `decimal.js` or bigint. The installed Supabase SDK parses ordinary JSON numeric tokens as JS numbers; an assertion that the result is a string does not change that behaviour (F-50, found during S6). **Never `parseFloat` a numeric column.** Money stays integer centavos end to end. Lint bans float coercions, and `toDecimal` rejects runtime numbers at the calculation boundary.

**5.2 Weighted-average recomputation must be serialised.** Two concurrent receipts of the same item both read the same `qty_on_hand` and `avg_unit_cost`, and both write an average computed from stale inputs. The fix is `SELECT … FOR UPDATE` on the item row inside the transaction, which means receiving must be a Postgres function, not a client-side sequence. Same for run completion, sale recording and adjustment. This is why section 2 exists. No design impact — the design already treats these as single confirmed actions.

**5.3 PostgREST caps every response at 1000 rows and `.limit()` cannot raise it.** Asking for 20,000 returns 1000, silently. Every list must page with `.range()`, and **every paged query must end its `.order()` chain with a unique column**, because paging over a non-unique sort returns rows in a different order per page — duplicating some and skipping others. I have seen this produce eight phantom duplicates and inflate a total on a previous project. Affects Items, Purchases, Sales, Movements, Production, and every report.

**5.4 The live profit panel cannot round-trip per keystroke.** Contribution profit updates as fees and shipping are typed. If COGS is fetched per change the panel lags and `aria-live` announces stale figures. The finished-goods `avg_unit_cost` and `qty_on_hand` must arrive in the sale form's **initial** payload, after which all arithmetic is client-side in decimal. This is why `/sales/new` reads those two columns in section 1.

**5.5 A footer total cannot be computed from a page of rows — and this one changed the design.** The sticky total across 5,000 rows needs its own aggregate query, so rows and total arrive separately. The design showed the total as always present. `Table total` now has a `Pending` state that keeps the bar and its label and skeletons only the figures — see `phase8-handoff.md` section 11.1. **Reported, not absorbed. Figma was updated first.**

**5.6 Figma's `Responsive` modes have no runtime equivalent.** They are a design-time convenience; in code they are Tailwind breakpoints. Documented in `phase8-handoff.md` section 5 so nobody hunts for a mode switch.
